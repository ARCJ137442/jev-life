## 零、还缺的两条：用户自备 key 的 LLM 后端

**现状**：`BACKENDS` 里有七条，其中与 LLM 有关的只有一条 —— `llmfree`
（「LLM 免费试用 1」），而且它是**代管**的：端与模型由服务端定，
broker 翻译也在服务端做。

**缺的是**：用户**自备 base URL / key / model** 的
**「OpenAI 兼容」**与**「Anthropic 兼容」**两条。用户手里有 DeepSeek 这类 key，
而今天没有地方填。

### ★ 这条带来的架构变化：broker 必须能在**客户端**跑

代管那条约定的路径是「客户端只发 Jev 形状 → 服务端翻译 → 上游」。
**用户自备 key 的没有那层服务端**（GitHub Pages 上更是连 Serverless 都没有），
所以**翻译必须发生在浏览器里**。

好在 `src/shared/llm-broker.ts` 本来就是纯函数、不碰 DOM 也不碰网络 ✓ ——
它可以在两边跑。`DecisionBackend.kind` 里预留的 `"llm-json"` / `"llm-tool"`
正是给这两条用的。

### 两种协议的形状差异（实测数据见第五节，别凭印象写）

| | OpenAI 兼容 | **Anthropic 兼容** |
|---|---|---|
| 路径 | `POST {base}/chat/completions` | `POST {base}/messages` |
| 认证头 | `Authorization: Bearer KEY` | **`x-api-key: KEY`** |
| 版本头 | — | **`anthropic-version: 2023-06-01`** |
| 系统提示 | `messages[0].role = "system"` | **顶层 `system` 参数**，不在 messages 里 |
| 输出上限 | `max_tokens` | `max_tokens`（**必填**） |
| 回包正文 | `choices[0].message.content` | **`content[]` 数组，取 `type === "text"` 那一段** |
| 回包结束原因 | `choices[0].finish_reason` | **`stop_reason`** |
| 用量 | `usage.prompt_tokens` / `completion_tokens` | **`usage.input_tokens` / `output_tokens`** |
| 推理 token | `usage.completion_tokens_details.reasoning_tokens` | 见下 |
| 工具调用 | `tools` + `tool_choice: "auto"` | `tools` + `tool_choice: {type:"auto"}`，回包是 `content[]` 里的 `tool_use` 块 |

> ⚠ **上表里 Anthropic 那列是「按协议文档推断」还是「实测」要分清。**
> 实现时**必须用真 key 各打一次**确认真实形状 —— 本项目的教训是
> `noul`/`boolean` 那次「文档说一套、网关做一套」，而四家网关里只有一家是异类。
> **不要在注释里写成已实测。**

### 其余要求

1. 两条都 `needsKey: true` / `managed: false` —— base URL 与 model 由用户填，
   **界面不能禁用模型输入**（那是代管才有的行为）
2. 两条都要支持**调用策略**（JSON / 工具循环）与**思考强度**（走同一套能力表）
3. ⚠ **CORS**：浏览器直连供应商可能被 CORS 拦下。**失败要报得清楚**
   （现在若不处理，会表现成 `fetch failed` —— 与「模型没答」长得一样）。
   Anthropic 官方 API 还需要一个额外的头才允许浏览器直连，这一点要查清并写进提示
4. 密钥**只在浏览器内存里**（这两条不经过服务端），**绝不落盘、绝不进日志**

### ★ 实现后的实测记录（2026-09-21，真 key）

上面那张表里的 Anthropic 那列**已经用真 key 逐条验过了**（Agnes 的
Anthropic 兼容端点 `POST {base}/messages`），**全部与协议文档一致**，没有
出现 `noul` / `boolean` 那种「文档说一套、网关做一套」：

> **补记（同日稍晚）**：下面这张 CORS 表里的官方端点那条，后来又用真 key
> 从浏览器直连验了一次 —— 通了，且两种调用策略都通。当时表里记的「403、
> 没能实测成功」是把探针的失败当成了端点的属性。**订正过程与教训见下方
> 「★ 那个 403 是探针的错」。** 也就是说这一列的形状**在两个端点上**都对得上，
> 不只是 Agnes。

| 项 | 实测结果 |
|---|---|
| 路径 / 认证头 / 版本头 | `POST /v1/messages` · `x-api-key` · `anthropic-version: 2023-06-01` ✓ |
| 顶层 `system`、`messages` 只有 user | ✓ |
| 回包正文 | `content[]` 里 `type === "text"` 的那一段 ✓ |
| 结束原因 | `stop_reason`（成功 `end_turn`、工具 `tool_use`、截断 `max_tokens`）✓ |
| 用量 | `usage.input_tokens` / `output_tokens`（**没有**推理 token 那一栏）✓ |
| 工具调用 | `tools[]` 用 **`input_schema`**、`tool_choice: {type:"auto"}`；回包是 `content[]` 里的 `tool_use` 块，**`input` 是对象不是字符串** ✓ |
| 工具续轮 | assistant 回述 `tool_use` 块 + user 里放 `tool_result` 块（`tool_use_id` 配对），回 200 ✓ |

**★ 一处只有端到端跑真 key 才会发现的差异**：

> **Anthropic 协议没有 `response_format`**，于是同一份提示词、同一个模型，
> OpenAI 那边回**裸 JSON**，Anthropic 这边回的是
> ` ```json\n{…}\n``` ` —— 模型自己套了 markdown 代码围栏。
>
> 不处理的话，**JSON 路径（`callPolicy` 的默认值）在这条协议上 100% 失败**，
> 而报错是「上游输出的不是合法 JSON」—— 看着像模型不听话，
> 真正的原因在协议少了一个字段。
>
> 修法：`fromLlmContent` 先剥掉**包住整段正文**的围栏（前后还有别的话就不剥，
> 容错仍然收窄）。纯函数的形状测试当时全绿，**这条是靠端到端跑出来的**。

**CORS 实测**（发 `Origin` 头看回包）：

| 端点 | 结论 |
|---|---|
| Agnes（两种协议同一个 host） | 预检 204，`Access-Control-Allow-Origin: *`、`Allow-Headers: *` ⟹ **可浏览器直连** |
| DeepSeek | 预检 200，回显 Origin，`Allow-Headers: authorization,content-type` ⟹ **可浏览器直连** |
| `api.anthropic.com` 官方 | 手工预检全部变体回 403 —— **但这条结论已被推翻，见下** |

### ★ 那个 403 是探针的错，不是端点的错（2026-09-21 订正）

上面那行原来记的是「没能实测成功」，并据此把整个后端标成「未实测」。
**这个结论是错的。**

真实浏览器直连**官方端点跑得通**（真 key，一次性 JSON 与工具循环两种调用策略
都验过）。官方端点认的是请求头
`anthropic-dangerous-direct-browser-access: true`（SDK 的 `dangerouslyAllowBrowser`
就是加它，不带会回 `CORS requests must set 'anthropic-dangerous-direct-browser-access' header`），
而 `shared/backend.ts` 的请求头构造**无条件带上它**。当时那个手工探针没发这个头 ——
所以 403 反映的是**探针没带那个头**，不是「浏览器连不上」。

> **教训**：一个失败的探针证明不了被探的对象不行，除非先排除「探针自己错了」
> 这个可能。这与本节规则 1 是同一类错 —— 那次探针把 429 限流读成了「模型不行」，
> 这次把「缺一个头」读成了「端点拒绝跨域」。**两次都是拿探针的失败直接当成了
> 对象的属性。**
>
> 代价也是真的：这条后端因此白挂了一段时间的「未实测」标签，界面文案还照着
> 这个错误结论写给用户看。当时的措辞是「本项目没有 Anthropic 的密钥」——
> 但「我没有 key 所以没验」和「这个端点验不了」是两回事，当时写成了后者。

**效力未定的两处**（如实记，别当成已验证）：

- `thinking: {type:"disabled"}` 被上游 200 接受，但**它到底有没有真的关掉思考
  没有测出来**（n=1：设它 11.6s / 不设 20.5s / `chat_template_kwargs` 6.7s，
  单次采样说明不了问题）。所以 broker 只保证**形状合法、上游不拒收**
- Anthropic 协议的 `usage` 里没有推理 token 那一栏 —— `reasoningTokens` 恒为 0，
  这正是 `TokenUsage` 注释里那条「用了推理却不报」的已知盲区

## 一、要建的是什么

`DESIGN.md` 第七节那条四层架构里，**中间两层还没建**：

```
游戏态势
   │   { model, state, questions }
   ▼
Jev 兼容 API          ← ✅ 已建（src/shared/backend.ts 的 DecisionBackend）
   │
   ▼
Jev–LLM API broker    ← ⏳ 待建：llm-json / llm-tool 两个适配器
   │
   ▼
LLM 提供商            ← ✅ systemone 已有；LLM 侧待接
```

**要建的东西**：

1. `llm-json` 适配器 —— 一次调用，要求模型输出符合 `answers` 形状的 JSON
2. `llm-tool` 适配器 —— 提供 `answer_questions` 工具，循环直到答完
3. UI 上的四个控件（第二节）
4. 统计采集 + 统计页面（第五节）

**`DecisionBackend` 的契约已经定好**（`src/shared/backend.ts:125`）：
`evaluate(req, hooks) → DecisionResult`，其中 `latencyMs` / `upstreamCalls` / `usage` / `costUsd`
都是**一等输出**。**适配器只管往里填，不改契约。**

## 二、★ 六条硬性要求

**这六条都是踩出来的，不是最佳实践。每一条后面附了它的实测依据。**

### 1 · 先看 HTTP 状态码，再看回包内容

`429` / `5xx` / 认证失败各有各的处置，**绝不能都归到「模型没给出答案」里**。

> **依据**：我自己的探针用 `j.choices?.[0]?.message?.content` 取内容、**没看状态码**，
> 于是 429 限流被统计成了「模型答不出来」。
> 一个「请求根本没被受理」在统计上表现成了「模型不行」——**症状与原因无关**，
> 正是本项目反复出现的那个母题。

### 2 · 默认关思维链

下发 `reasoning_effort: "none"`。

> **依据**：两个后端，思维链开→关，成功率 `5/8 → 8/8`（agnes）与 `0/4 → 4/4`（deepseek）；
> 耗时降到 1/5 至 1/40；推理 token 归零。
> **更硬的理由**：它**从结构上消灭了「推理吃光预算」这个失败模式**——
> 而那是观察到的**唯一**失败原因。

**两种有效写法**（跨后端）：

| 写法 | 该后端 | 备注 |
|---|---|---|
| `reasoning_effort: "none"` | agnes（SGLang）✓ · deepseek ✓ | **首选**，兼容面比预期宽 |
| `chat_template_kwargs: {"enable_thinking": false}` | agnes ✓ | 备选 |

**无效或被忽略的**（别在这上面花时间）：`enable_thinking: false` 只是**减少**；
`thinking: {type:"disabled"}` **被忽略**；`reasoning_effort: "minimal"` **400**。

### 3 · 空 `content` + `finish_reason: "length"` 必须当失败

不能把 `content` 为空当正常回包。

> **依据**：这是失败的唯一形态。实测 `max_tokens: 20` 时 20 个 token 全被思维链吃掉，
> `content` 返回**空字符串**、`finish_reason: "length"` —— **HTTP 200，看着像成功，
> 实际什么都没答**。

### 4 · `reasoningTokens` 单独记账

`usage.completion_tokens_details.reasoning_tokens`（OpenAI 兼容协议）。
**没报就是 0，不是 `null`** —— 与 `costUsd` 的语义不同：「不知道价格」和「没有推理」是两回事。
（`TokenUsage.reasoningTokens` 已在 `src/shared/backend.ts:59` 备好。）

> **依据**：推理 token 可占输出的 **100%**（4000 个全烧在推理上、可用答案 0 个）。
> 统计页要按「后端 × 模型 × 调用配置」比成本，而**思维链开关正是最大的那个配置变量**；
> 少了这一栏，「**关思维链省了多少钱**」这个故事就算不出来。

### 5 · UI 的枚举不能直接当请求体下发

broker 必须持有**后端能力表**：支持就发，不支持就**不发**（留空用后端默认），
并在 UI 标注「该后端不支持，已降级为默认」。

> **依据**：该后端的 `reasoning_effort` 合法值是 `none | low | medium | high | max`，
> **没有 `xhigh`**。UI 的六档是面向多后端的**并集**，直接发出去会 **400 把整个请求打掉**——
> 一个「界面能选、一选就把决策请求打成 400」的陷阱，而且报错离原因很远。

### 6 · 显式设超时

> **依据**：Node 的 `fetch`（undici）默认 **5 分钟**掐 headers。
> `max_tokens=32000` 那轮两个 flash 模型都栽在 `UND_ERR_HEADERS_TIMEOUT` 上。
> （`DEFAULT_TIMEOUT_MS = 60_000` 已在 `src/shared/backend.ts:83` 备好。）

## 三、实测行为基线（实现时的对照）

提示词：8×8 棋盘 + 6 题 `noul` + B3/S23，`response_format: json_object`。

| 后端 | 思维链 | 成功率 | 耗时 | 推理 token |
|---|---|---|---|---|
| `agnes-2.5-flash`（免费） | 开 | 5/8（63%） | 16.6–64.0 s | 最高 **4000（全烧光）** |
| `agnes-2.5-flash` | **关** | **8/8（100%）** | **1.1–4.9 s** | **0** |
| `deepseek-flash`（付费） | 开 | **0/4（0%）** | 16.1–18.8 s | **16000（全烧光）** |
| `deepseek-flash` | **关** | **4/4（100%）** | **0.8–1.1 s** | **0** |

**付费后端在思维链开时反而更差** —— 所以「LLM 不稳定」不是某一家的毛病，
是**推理模型的默认行为**，broker 的默认姿态应当面向所有推理后端。

### 路径差异（同后端、同 N=6、同关思维链）

| 路径 | 墙钟 | 备注 |
|---|---|---|
| `llm-json` | **1.1–4.9 s** | 形状靠提示词约束 |
| `llm-tool` | 8.9 / 17.3 s | 形状由 schema 强制 |

**倾向 JSON 作默认、工具作对照** —— 两条都实现，因为这本身就是可对照的变量。

### 批量：模型总是**一轮全答**

| N | 上游调用 | 每轮答几个 | 墙钟 |
|---|---|---|---|
| 1 | **1** | 1 | 5.1 / 6.9 s |
| 6 | **1** | 6 | 8.9 / 17.3 s |
| 12 | **1** | 12 | 11.4 / 12.6 s |
| 24 | **1** | 24 | 7.4 / 30.8 s |

**8/8 全成功，上游调用次数恒为 1。**

**两个推论**：
- **broker 不需要主动限制每轮批量** —— 模型自己收敛到「全答」
- 但「一次可答 ≥1 个」的形状**仍然必须保留** —— 它的价值不是「让模型分多轮」，
  而是**不让模型被「一次只能答一个」绑住**。若把工具设计成一次一题，24 题就是 24 次往返

> ⚠ **`remaining` 回包尚未被验证有用** —— 在这 8 次里它从未被用到（永远一轮答完，
> 循环第二轮都没进）。**不要删**（低成本保险），但**也别声称它被验证过**。
> 要测它，得构造一个必然分多轮的场景（N 远大于单次输出上限）。

### 限流：按 **token** 计，不是按请求数

| 负载 | 结果 |
|---|---|
| 14 次**轻请求**（关思维链，约 60 token/次）连发，31 秒内 | **14/14，零限流** |
| 约 40–50 次**重请求**（开思维链，4000 token 预算）分散半小时内 | 多次 429 |

**关思维链把单次 token 压到百分之一量级** —— 跑分规模跟着放大。

### 后端身份（便于排查）

`agnes` 是**自托管的 SGLang**（从 400 的报错栈看到
`/usr/local/lib/python3.12/dist-packages/sglang/srt/entrypoints/http_server.py`），
模型名是 rebrand。**「agnes-2.5-flash」不是某个已知厂商的模型。**

## 四、UI 控件规格

四个控件，**只在选用 LLM 后端时出现**，但**配置要持久化**（换回 Jev 再换回来，设置还在）。

| 控件 | 取值 | 默认 |
|---|---|---|
| **思维链** | 开 / 关 | **关** |
| **是否允许思考** | 是 / 否 / 留空 | 留空 |
| **思考强度** | 无 `none` / 低 `low` / 中 `medium` / 高 `high` / 超高 `xhigh` / 最强 `max` / 默认（留空） | **留空** |
| **调用策略** | JSON 输出 / 工具循环 | JSON |

### ★ 思考强度必须带 UI 警示

**实测六个档位，只有 `none` 与「留空」能跑通**：

| `none` | 留空 | 低 | 中 | 高 | 最强 |
|---|---|---|---|---|---|
| **3/3** | **3/3** | 1/3 | **0/3** | 1/3 | 1/3 |

**四个显式档位全部劣于不设**，而且**不是单调的** —— 规律是「只要设了就变差」。
推理 token 与成功率**无关**（中档烧得最多，却是唯一 0/3）。

**处理方式**：**保留控件、默认留空、把实测写进提示**，让人知情地选：

> *「实测：显式设置本项会显著降低成功率（3/3 → 0–1/3）。默认留空。」*

**不删它的理由**：只有一个后端的数据，别家可能不同；且它本身仍是有价值的实验变量
（`reasoning_effort` 的语义是「让模型多想」，而这里「多想」明确是负收益 —— 这现象值得留着复现）。

### 两个思考控件的耦合

`是否允许思考` 与 `思考强度` 的 `none` 语义重叠。做法：
前者选「否」时**强度置灰显示 `none`**；强度选 `none` 时前者自动显示「否」。
两者最终归一到同一个下发字段（按后端能力分别落到 `reasoning_effort` 或
`chat_template_kwargs.enable_thinking`）。

### 统计必须可重置

否则跑完一轮对照，第二轮的数据会被第一轮污染。

## 五、统计指标

**分组键是 `后端 × 模型 × 调用配置`，不是模型。**

> **依据**：同一模型开/关思维链是两个不同的东西（**100% vs 63%**）。
> 混在一起算平均，得到的数字谁也不代表。

| 指标 | 为什么非有不可 |
|---|---|
| **单次成功率** | 必须与「重试后的成功率」分开，否则看不出模型的真实能力 |
| 重试 N 次后的成功率 | 决定「配几次重试才够用」 |
| 重试次数分布 | 平均值会掩盖「一半一次过、一半要五次」 |
| **★ 限流比例（429）** | 不单列就会被算进「模型不行」——**已经栽过一次** |
| **延迟的分位数**（中位 / p90）而非平均 | 实测见过 1.1 s 与 190.9 s，平均值没有意义 |
| 推理 token 占比 | 关思维链前后是 0% 与 90%+ |
| 成本 | **必须标注价目表的日期**（价格会变） |

「调用配置」至少含：**思维链开关 / 思考强度 / 协议（JSON 或工具）/ 问题数**。

## 附录 · 方法论上的两个坑

**这两条都是我在本轮实测里真踩过的，实现时同样适用。**

### 报数字前先问「来自几次采样」

我在**同一份提示、同一个模型**上测到过 `0/4`、`1/4`、`2/4`、`4/4`。
那个被我写进文档的「约 50% 成功率」是**小样本噪声**，不是规律。

**`n=1` 不叫测量，叫观察。**

### 报「模型不行」前先看 HTTP 状态码

见第二节第 1 条。**请求没被受理**与**模型答不出来**，在代码里长得一模一样。

### 做变异测试前先确认改动真的生效

本轮协调者与多个 agent 都因 `sed` 没匹配上而**测了没改过的代码**，得出了假结论。
改完先 `command grep` 一眼。
